# Manifiesto Conceptual: Orquestador `i18n.ts` (Server-Side)

## 1. Rol Estratégico y Propósito

Este aparato es el **cerebro de la internacionalización en el lado del servidor**. Actúa como el puente crítico entre el `locale` detectado por el middleware y los archivos de contenido (`.json`) siguiendo la Arquitectura Atómica Espejada (IMAS). Su propósito es garantizar la correcta configuración de `next-intl` para la carga dinámica de mensajes, asegurar la coherencia de los locales soportados y proporcionar una trazabilidad de élite.

Como orquestador de Server Components, sus responsabilidades son:

1.  **Validación de Locale Canónica:** Valida el `locale` de la petición contra la Única Fuente de Verdad (SSoT) definida en `src/lib/navigation.ts`, rechazando locales no soportados con `notFound()`.
2.  **Carga Dinámica y Ensamblaje de Mensajes (IMAS):** Itera sobre el `messagesManifest` (SSoT de los namespaces) para cargar de forma perezosa y ensamblar todos los módulos de traducción atómicos para el `locale` solicitado. Utiliza `setNestedProperty` para construir un objeto de mensajes anidado, cuya estructura final es `AbstractIntlMessages`, asegurando la compatibilidad con `next-intl`.
3.  **Configuración de `next-intl`:** Provee a `next-intl` con el conjunto correcto de mensajes completamente ensamblados y otras opciones de configuración global (ej. `timeZone`).
4.  **Trazabilidad y Observabilidad de Élite:** Envuelve su ejecución con `withCorrelationId` y utiliza el `serverLogger` para registrar el flujo detallado, advertencias y errores durante el proceso de carga de i18n. Esto garantiza una visibilidad completa y facilita el diagnóstico de cualquier problema.

Esta arquitectura es fundamental para permitir la pre-renderización estática (SSG) de todas las páginas internacionalizadas sin errores por falta de archivos o inconsistencias de configuración, contribuyendo a un `build` limpio y eficiente.

## 2. Arquitectura y Flujo de Ejecución

Este es un Server Component especial que se integra con el ciclo de vida de Next.js para `next-intl`.

3. Contrato de API
default getRequestConfig({ locale }): Promise<{ messages: AbstractIntlMessages; timeZone?: string }>:
Propósito: Función principal para la configuración de next-intl en el servidor.
Parámetros:
locale: string: El identificador del locale para el cual se deben cargar los mensajes (ej. "it-IT").
Retorno: Una promesa que resuelve a un objeto con los messages completamente ensamblados y tipados como AbstractIntlMessages para el locale, y, opcionalmente, una timeZone por defecto para formatos consistentes.
Efectos Secundarios: Puede invocar notFound() si el locale no es válido. Emite logs estructurados a través del serverLogger con correlationId para trazabilidad.
4. Zona de Mejoras Nuevas (Valor al Proyecto)
Tipado con Zod para Módulos de Mensajes (Tiempo de Build): Implementar un script que, en tiempo de build, genere schemas Zod a partir de los messagesManifest y los utilice en i18n.ts para validar la estructura de cada módulo de mensajes cargado. Esto blindaría el sistema contra archivos .json malformados o inconsistentes en su estructura.
Gestión Avanzada de fallbackLocale a Nivel de Mensaje: Extender la lógica de getRequestConfig para que, si un namespace no tiene traducciones para el locale solicitado, intente cargar su versión del defaultLocale (o un fallbackLocale específico configurado) antes de registrar una advertencia. Esto mejoraría la experiencia del usuario y la robustez frente a traducciones incompletas.
Contexto de Zona Horaria Global y Formatos: Formalizar la configuración de timeZone y formats dentro de la función getRequestConfig para garantizar que todos los componentes que usen useTranslations para formatear fechas y números lo hagan de manera consistente y localizada.
Integración con Cache de Traducciones: Para evitar la recarga y el procesamiento de módulos de mensajes que no han cambiado, se podría implementar una estrategia de caché (ej., utilizando React.cache de Next.js o una caché en memoria controlada) dentro del bucle de carga en i18n.ts. Esto mejoraría el rendimiento en el servidor para peticiones subsecuentes.
Monitoreo de Errores de import() Granular: Mejorar la gestión de errores dentro del bucle for...in messagesManifest para distinguir entre diferentes tipos de fallos (ej. error de I/O al cargar el archivo, error de parseo de JSON, error de validación de esquema si se implementa). Esto proporcionaría diagnósticos más precisos en los logs.
