# Manifiesto Conceptual: `i18n.ts`

## 1. Rol Estratégico y Propósito

Este aparato é o **Corazón da Orquestración de Internacionalización (i18n)**. Actúa como o punto de entrada canónico que `next-intl` utiliza para cargar dinamicamente as traducións necesarias para cada petición.

A súa única e crítica responsabilidade é consumir o `messagesManifest`, iterar sobre el, cargar os módulos de mensaxes correspondentes ao `locale` actual e ensamblalos nunha única estrutura de obxecto aniñado utilizando o helper `setNestedProperty`. Isto desacopla completamente a lóxica de carga da definición de compoñentes, permitindo unha arquitectura de i18n escalable (IMAS).

## 2. Arquitectura y Flujo de Ejecución

É un módulo de configuración de servidor que exporta unha función `async`.

```mermaid
graph TD
    A[Petición a `/{locale}/...`] --> B{`next-intl` invoca `getRequestConfig`};
    subgraph "Lógica de `i18n.ts`"
        B --> C[Valida o `locale`];
        C --> D[Itera sobre `messagesManifest`];
        D -- Para cada namespace --> E(Invoca `import()` dinámico);
        E --> F[Extrae as traducións para o `locale`];
        F -- Usa --> G{Helper `setNestedProperty`};
        G --> H[Constrúe o obxecto `messages` aniñado];
    end
    H --> I[Retorna `{ messages }` a `next-intl`];
3. Contrato de API
Exportación por defecto: getRequestConfig(config: { locale: string }) => Promise<{ messages }> - A función que next-intl espera.
4. Zona de Melhorias Futuras
Carga Selectiva de Namespaces: A implementación actual carga todos os ficheiros de mensaxes para cada páxina. Unha optimización de elite sería modificar a lóxica para que, baseándose na ruta, só cargue os namespaces de mensaxes que esa páxina específica necesita, reducindo a pegada de memoria.
Cacheo de Mensaxes: Para aplicacións renderizadas no servidor (SSR), o obxecto de mensaxes ensamblado para un locale podería ser cacheado en memoria (React.cache) para evitar o traballo de ensamblaxe en cada petición.
Integración cun Sistema de Xestión de Traducións (TMS): A lóxica de carga podería ser adaptada para obter as traducións desde unha API dun TMS (como Lokalise ou Phrase) en lugar de ficheiros JSON locais, permitindo actualizacións de contido sen redesplegar a aplicación.
Manexo de Fallback de Namespaces: Implementar unha lóxica que, se un namespace non ten traducións para un locale específico, cargue automaticamente as traducións do defaultLocale para ese namespace.
Probas de Integración: Escribir probas de integración que simulen a chamada a getRequestConfig para varios locales e verifiquen que a estrutura do obxecto messages xerado é a correcta.
